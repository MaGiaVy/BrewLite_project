## Integration Test Traceability Matrix

| Requirement | Test | Observable acceptance |
|---|---|---|
| FR-05 / AC-05.1 | INT-T01 | `POST /orders` creates `PENDING`; successful `POST /payments` changes it to `PAID`, persists one payment, decrements stock and adds loyalty points. |
| FR-05 / AC-05.3 | INT-T03 (`orders-payments.int.spec.ts`) | Two concurrent orders for one remaining unit produce one `201` and one `400` or `409`; stock ends at zero. |
| FR-05 / AC-05.4 | INT-T04 (`orders-payments.int.spec.ts`) | A failed payment persists `PAYMENT_FAILED` without a second stock deduction; retry persists `PAID`. |
| FR-04 / AC-04.4 | INT-T05 (`orders-payments.int.spec.ts`) | `POST /orders` without a bearer JWT returns `401`. |
| Payment idempotency | INT-T02 (`orders-payments.int.spec.ts`) | Reusing an idempotency key returns the original payment and leaves exactly one `Payment` row and one loyalty-point increment. |
| RBAC, Concurrency & Sandbox Security | Cases 1–10 (`security-concurrency.int.spec.ts`) | Verifies `tokenVersion`/`isActive` revocation, `admin@brewlite.vn` protection, atomic `UserVoucher` & max-5 pending `SELECT ... FOR UPDATE`, `403` sandbox/cross-role payment guards, beverage size `ALL` / inactive voucher / `409` logged ingredient deletion checks, catalog `redeemPoints`, `STAFF` projection on `/products/:id/sold-out`, and KDS queue preservation. |

## Test configuration

- `TEST_DATABASE_URL` points to an isolated PostgreSQL database.
- The integration suite runs `npx prisma migrate reset --force --skip-seed` once before the suite.
- Each test removes its own persisted rows and seeds a unique user/product.
- CI provisions PostgreSQL as a service; local runs require PostgreSQL and `TEST_DATABASE_URL`.
- The API test client signs HS256 JWTs with `JWT_SECRET`; production endpoints do not accept the legacy `x-user-id` header as authentication.
